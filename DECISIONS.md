# DECISIONS.md — LYFESTYL

Architecture & product decisions, with rationale, so the morning review is fast. UI rules in `CLAUDE.md` are law; everything here lives within them.

---

## 1. Platform / toolchain
- **Target:** iOS 26.0+ (built & verified against the iOS 26.5 SDK, Xcode 26.5, Swift 6.3).
- **Language version:** the project ships `SWIFT_VERSION = 5.0` with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` + `SWIFT_APPROACHABLE_CONCURRENCY = YES`. We keep these (MainActor-by-default is exactly what a SwiftUI app wants) and write modern Swift 6-style code (`@Observable`, async/await, actors) on top. We did **not** force `-swift-version 6` strict-concurrency because the Supabase SDK + our actors compile clean under approachable concurrency and flipping it risks churn for no user-visible gain.
- **Force dark mode app-wide** (`.preferredColorScheme(.dark)` at the root). Solarized Dark is the only palette; there is no light variant.

## 2. Why these APIs (all verified against the on-disk SDK before use)
The single biggest failure mode called out in `CLAUDE.md` is hallucinated iOS 26 symbols. Before writing any code we read the actual `.swiftinterface` files in the iOS 26.5 SDK and pinned exact signatures:
- **FoundationModels** — `SystemLanguageModel.default.availability`, `LanguageModelSession(model:tools:instructions:)`, `respond(to:generating:options:)`, `streamResponse(to:generating:)`, `@Generable`, `@Guide`, `GenerationGuide.anyOf/.range/...`, `GenerationOptions(sampling:temperature:)`. Verified.
- **Speech** — `SpeechTranscriber(locale:preset:)`, `SpeechAnalyzer(modules:)`, `AnalyzerInput(buffer:)`, `analyzer.start(inputSequence:)`, `transcriber.results` (AsyncSequence of `Result` with `.text: AttributedString`), `AssetInventory` for model download. Verified.
- **Liquid Glass** — `.glassEffect(_:in:)`, `Glass.regular/.clear` + `.tint/.interactive`, `GlassEffectContainer`, `.glassEffectID(_:in:)`, and the `.glass` / `.glassProminent` button styles. Verified (in SwiftUICore).
- **Sign in with Apple** — `SignInWithAppleButton(_:onRequest:onCompletion:)` + `.signInWithAppleButtonStyle`, `ASAuthorizationAppleIDCredential.identityToken/email/fullName/user`. Verified.
- **Swift Charts** — present in SDK; standard `Chart { ... }` marks.
- **Supabase Swift SDK** — the only off-device dependency; verified against official docs (see README) rather than the SDK (not on disk until resolved).

## 3. The on-device pipeline (the heart)
- **Guided Generation, never JSON parsing.** Output is a `@Generable struct EntryBreakdown` containing `[CategoryInsight]`. The model returns typed Swift values directly via `session.respond(to:generating: EntryBreakdown.self)`.
- **Determinism for trend comparability.** We call the model with `GenerationOptions(sampling: .greedy)` so the same entry yields stable estimates — important because LYFESTYL's value is *trends over time*.
- **Availability handling.** `SystemLanguageModel.default.availability` is checked up front and surfaced as a real UI state: `available`, `deviceNotEligible`, `appleIntelligenceNotEnabled`, `modelNotReady` (downloading). We **never** lose the raw entry — it is saved first, then enriched. If the model is unavailable the entry is stored raw with `status = pending` and re-processed automatically when the model becomes available.
- **Focused prompt.** The ~3B model is tuned for extraction/classification, not trivia, so instructions are tight: "You are a health-journaling analyst. Break the entry into the categories actually present. Estimate tangible numbers. Rank each category." Full text in `InsightEngine.swift`.

### Scoring / estimation system (proprietary, versioned: `schemaVersion = 1`)
- **Four categories:** `NUTRITION`, `ACTIVITY`, `SLEEP`, `HEALTH`. One entry can populate several; only categories actually mentioned are emitted.
- **5-point rank:** `EXCELLENT > GOOD > OKAY > BAD > AWFUL`, mapped to a numeric `rankScore` 5→1 for trend math, and to palette colors per `CLAUDE.md` (EXCELLENT→green, GOOD→cyan, OKAY→yellow, BAD→orange, AWFUL→red).
- **Tangible estimates** are modeled as *optional typed fields* on `CategoryInsight` rather than free-form key/value pairs. Free-form labels ("kcal" vs "calories" vs "energy") destroy trendability; fixed columns guarantee a clean time series. Fields: `calories, proteinGrams, carbsGrams, fatGrams, waterOunces` (nutrition), `activeMinutes, distanceMiles` (activity), `sleepHours` (sleep). HEALTH is qualitative (rank + detail). All optional — the model fills only what's relevant.
- **Rank rubric** is spelled out in the prompt so ranks mean the same thing across entries and over time (e.g. SLEEP: EXCELLENT ≈ 7.5–9h restful; AWFUL ≈ <4h or badly disrupted). This is what makes consistent journaling produce a meaningful trend line.

## 4. Data model & storage
- **Supabase is authoritative.** Three tables: `profiles`, `entries`, `insights` (one entry → many insights, one per category). Insights are stored relationally with metric **columns** so trend queries are trivial `select` + group-by. Full SQL is in `README.md` and `supabase/schema.sql`.
- **Local cache for offline/optimistic UI** (allowed by `CLAUDE.md` §4.2). A file-based JSON store (`LocalStore`, actor-guarded) in Application Support mirrors entries+insights for instant, offline-capable rendering and is reconciled against Supabase on launch/refresh. We deliberately did **not** use SwiftData/Core Data as a source of truth.
- **Offline-safe entry handling.** Submit flow: (1) write entry to local cache immediately (never lost), (2) enqueue a sync+process job, (3) push raw entry to Supabase, (4) run the on-device breakdown, (5) push insights + mark processed. Any step can fail (no network, model busy/unavailable) without data loss; the `EntryQueue` actor persists pending jobs and retries on app-foreground, connectivity return, and model-availability change.

## 5. Auth
- **Sign in with Apple only**, native `SignInWithAppleButton`, wired to Supabase via `auth.signInWithIdToken(.init(provider: .apple, idToken:, nonce:))`.
- **Nonce flow (security-critical):** generate a random raw nonce → SHA256 → set the **hashed** nonce on the Apple request → pass the **raw** nonce to Supabase. This binds the Apple assertion to our request and is required for Supabase to validate the token.
- Session persisted by the SDK; app is gated behind auth; sign-out and token refresh handled by the SDK's auth state stream.

## 6. Secrets
- `LYFESTYLE/Secrets.plist` (gitignored, bundled) holds `SUPABASE_URL` + `SUPABASE_PUBLISHABLE_KEY`. Committed template: `Secrets.example.plist`.
- The **publishable** key is client-safe and intentionally the only key in the app. The **secret** key is never stored in the app (server-only). If the plist is missing, the app shows a clear "configuration needed" state instead of crashing (`// TODO: user provides`).

## 7. Open forks resolved by default (flag if you disagree)
- **Metrics as fixed columns, not free-form pairs** — chosen for trendability (see §3). Reversible: schema is versioned.
- **File-based cache over SwiftData** — chosen for an unambiguous "Supabase is the source of truth" story and zero model duplication.
- **Two tabs (Journal, Log)** via `TabView`, Journal first — matches the "open → type immediately" thesis.
- **Determinism (`.greedy`) over creative variety** — chosen because this is a measurement tool, not a chat toy.
- **New publishable/secret key format** assumed accepted by `SupabaseClient(supabaseKey:)` (it is sent as the `apikey`/bearer header exactly like the legacy anon key). Verified via the Supabase Swift verification pass.

## 8. LYFE/STYL surface rework (history-first + in-place create)
- **LYFE is now the entry surface = full history + create.** Previously "Journal" was a single composer and "Log" was the history; they're merged. LYFE shows every entry as an atomic, timestamped Apple-Journal-style card (no TODAY/day grouping — `entriesByDay` removed). Tapping a processed entry opens the existing `EntryDetailView` breakdown.
- **STYL = cumulative insight (interim).** With history moved to LYFE, STYL now hosts the existing Swift Charts `TrendsView` via a thin `StylView` wrapper. A fuller STYL rework (narrative/cumulative descriptions) is intentionally deferred per the user; `LogView` was deleted (fully absorbed).
- **In-place create flow, not a pushed screen.** The composer is an overlay inside the LYFE `NavigationStack` toggled by `isEditing`, so a single persistent trailing toolbar button morphs plus ⇄ checkmark (`.contentTransition(.symbolEffect(.replace))`, `ToolbarItemGroup` for stable identity + deterministic `•••`→`✓` order). The tab bar is hidden while editing (`.toolbar(.hidden, for: .tabBar)`). This also fixes the prior keyboard bug: the editor is full-screen with a top-anchored field and the voice control on a bottom safe-area inset, so the keyboard never shifts the surrounding layout.
- **Save semantics.** Both the checkmark and the back chevron save; the `•••` menu discards. Saving routes through the composer (`commitTrigger`) so an in-flight recording is finalized (`speech.stop()` drained + merged) before persisting. Empty drafts just close. Success haptic keys off `JournalStore.savedTick` (bumped only on a real insert) so it never fires on delete/refresh/sign-out.
- **Inline on-device voice replaces the recorder sheet.** (Superseded by §13.) `EntryComposer` originally drove `SpeechService` directly with a live transcript streaming into the field. Voice has since been rebuilt into a full conversational mode (§13); the mic now opens that, and what you say flows back into the same draft.
- **Processing affordance.** Pending/processing rows are dimmed and non-openable, cycling a bank of reflective gerunds (`ProcessingIndicator` / `ProcessingWords`) Claude-Code-style; they become openable once `.processed`.

## 9. STYL = the "how am I doing" status surface (this build)
- **STYL is now the profile / health / life-status page**, Garmin-Body-Battery in spirit: a hero ring + qualitative headline, per-category standings, a measured (HealthKit) lane, the daily check-in, and the full Swift Charts `TrendsView` and account/`ProfileView` one tap away. No word bombs.
- **The honesty contract (load-bearing).** Journal inference yields ONLY qualitative reads: a `Rank` standing, a `TrendDirection`, recency, and a 1–5 score that drives a ring/bar fill but is **never shown as a number**. The only figures rendered as numbers are `MeasuredMetric`s from HealthKit. This is enforced structurally: `StatusEngine` copies measured values through and never fabricates one, and the check-in's model schemas have no numeric field at all (see §11). New build-check: *every number on STYL is traceable to measured data.*
- **`StatusEngine` (pure, like `TrendCalculator`).** Standing = mean rank score over the last 7 days → `Rank(roundedScore:)`. Trend = recent-7-day mean vs the prior 7 days, with a ±0.4 band (else `steady`; `insufficient` when a side is empty). Recency from the latest entry day. Overall = mean of available category scores → a qualitative headline band + a computed, number-free subtitle. Provenance (`StandingSource`: journal / measured / check-in) is tracked so the UI attributes each standing honestly.
- **HealthKit can SHARPEN a read.** When a category has gone quiet in the journal but HealthKit has a defensible measurement, `StatusEngine` derives the standing from the measurement (SLEEP from measured hours, ACTIVITY from exercise minutes) with conservative, documented thresholds, flagged `from Apple Health`. Absence of a measurement (no watch, 0 exercise) never produces a *bad* standing — absence of data is not bad data.

## 10. Apple HealthKit (measured lane)
- **Read-only.** `HealthService` requests read access to: step count, active energy, exercise minutes, walking/running distance, resting heart rate, HRV (SDNN), respiratory rate, blood oxygen, sleep analysis, mindful minutes. We never write. Usage string `NSHealthShareUsageDescription` + the `com.apple.developer.healthkit` entitlement are added; HealthKit reads happen on-device.
- **Modern async queries, verified against the iOS 26.5 SDK before use** (CLAUDE.md §2): `HKHealthStore.requestAuthorization(toShare:read:) async`, `HKStatisticsCollectionQueryDescriptor.result(for:)` (cumulative-sum/discrete-average daily buckets), `HKSampleQueryDescriptor.result(for:)`, `HKSamplePredicate.quantitySample/categorySample`, `HKQuery.predicateForSamples`, the `HKCategoryValueSleepAnalysis.asleep*` cases. Sleep = summed asleep-stage durations over a 2pm-anchored nightly window; baselines = trailing-14-day averages.
- **Empty store is a normal state.** No watch / no data / read-access-not-granted ⇒ an empty `HealthSummary`; STYL silently falls back to the journal-inferred picture and shows a "Connect Apple Health" affordance. HealthKit deliberately does not reveal *read*-grant status, so we treat a completed authorization sheet as "asked" and let emptiness be normal. We never simulate or backfill data.

## 11. The daily check-in (medical-style questioning)
- **Deterministic selection, model only phrases.** A pure-Swift `CheckInPlanner` scores candidates by information gain and returns 0–3 `CheckInSlot`s (often 1, sometimes none — it prefers silence over a weak question). Candidates, highest first: a HealthKit **anomaly** vs the user's own baseline (resting HR up, HRV down, measured sleep short — each carries the real number as honest context), a **slipping** qualitative trend, a **quiet** category (especially MIND/SOCIAL, which HealthKit can't measure), **diet** quality (food is barely measurable), a periodic **mood** read, and **screen-time** self-report. The 3B model is never trusted to prioritize — selection is auditable Swift.
- **Two metric-free model passes** (fresh `LanguageModelSession`, `.greedy`, matching `InsightEngine` exactly — verified `exceededContextWindowSize` is the failure mode that makes transcript reuse wrong): Pass 1 phrases the agenda into warm questions + tappable options; Pass 2 fuses the answers into QUALITATIVE `StandingAdjustment`s. **No schema in `CheckInModels.swift` has a single numeric field**, so a one-tap answer can never mint a fake calorie/hour. Both degrade gracefully: templated phrasing when the model is unavailable, and fixed-format slots (mood scale, screen-time band) map to a `Rank` deterministically with no model at all.
- **Answers re-grade a SEPARATE standings lane, never the journal.** We deliberately do NOT run answers through the `breakdown` pipeline (that path would estimate calories/sleep-hours, minting fake numbers, and pollute LYFE with text the user never wrote). Instead each adjustment upserts `category_standings` (qualitative only). `StatusEngine` blends it confidence-gated: a LOW-confidence answer moves only the trend/recency; MEDIUM/HIGH may correct a standing; a quiet category is un-quieted. Persisted in `check_ins` (raw Q&A for provenance) + `category_standings`. One check-in per day, with per-(category,intent) cooldowns; "Not now" marks the day handled so it never re-nags.

## 12. Screen time (honest within Apple's rails)
- **The hard constraint:** Apple does not let third-party apps read raw Screen Time totals. The public surface is FamilyControls (individual authorization), DeviceActivity, and `DeviceActivityReport`, and usage data can only be **rendered inside a sandboxed report extension** — it cannot be exported out of that extension into the app process to feed the model. There is no API that returns total screen-time minutes.
- **Our choice:** the **self-report** path the prompt blesses as legitimate. A check-in slot asks for a coarse phone-use **bucket** (`Barely / A normal amount / More than I'd like / Way too much`), framed honestly ("iOS keeps Screen Time private, so your best guess"), stored as a **label** in `screen_time_reports` (never a minute count), and fed to the model as qualitative context that can nudge the MIND standing. No fabricated minutes, ever.
- **What we did NOT build, and why:** a `DeviceActivityReport` extension target. It would require the **Family Controls entitlement, which needs explicit Apple approval for App Store distribution** and cannot be code-signed by a normal development team, so adding that target would break the green build in this environment and still could not export totals to the app. Documented here as a possible future addition (display-only) if/when the entitlement is granted; the self-report path remains the only way to get phone-use signal *into the model*.

## 13. Voice mode (rebuild)
- **Voice is a full-screen transcription mode with a reactive orb.** Tapping the mic in the composer opens a calm, immersive experience: a living **orb** (`VoiceOrb`, drawn content via `TimelineView`, Solarized accents) that breathes while idle and visibly swells, rings, and glows in time with your voice while it listens. You talk like a voice memo; the live transcript builds beneath the orb; tapping Done drops the text into the draft.
- **No assistant.** An earlier version had the model ask spoken follow-ups (a conversational agent); that was removed by request. Voice mode is pure on-device transcription now: just you talking, captured. (`VoiceFollowUp`, the follow-up engine methods, and the `AVSpeechSynthesizer` layer were deleted.)
- **Everything on-device.** Speech recognition runs on-device (`SpeechTranscriber` via `SpeechService`); nothing is sent anywhere. `VoiceConversation` is a single continuous listening session (no turns, no audio-session juggling): start listening, stream the transcript, finalize on Done.
- **Mic reactivity.** The orb is driven by `SpeechService.inputLevel` with a strong, snappy spring so each syllable visibly moves the core, the ring, and the glow, the clear "it's alive" feedback voice UIs need.
- **Seamless with the entry system.** The transcript flows back into the `EntryComposer` draft (`usedVoice = true`); the user reviews and saves with the existing checkmark, so it runs the exact same breakdown pipeline as a typed entry. No new entry path, no special-casing.
- **Graceful degradation.** No speech model on the device shows a clean "Voice isn't available, type instead" state; the user can tap Done at any moment. `VoiceRecorderView` (the old sheet) stays deleted; the prior inline-dictation machinery in `EntryComposer` was removed in favor of this.

## 14. Backend migration: Supabase to CloudKit (2026-07-12)
- **Persistence and auth moved from Supabase to Apple CloudKit.** The app now has zero external services. `CloudKitService` replaces `SupabaseService` and talks directly to the CloudKit **private database** in container `iCloud.Moments.LYFESTYLE`, one `Entry` record per journal entry. Auth stays Sign in with Apple, but there is no token exchange with a backend anymore; the iCloud account itself owns the data, and the private database is auto-scoped to it.
- **Why.** This is a better fit for `CLAUDE.md`'s "first-party Apple" rule than a hosted Postgres project ever was. It removes the last external dependency, the last set of secrets (`Secrets.plist`, publishable key), and the last piece of infrastructure a solo dev has to run or pay for. CloudKit's private database gives per-user isolation for free, there is no Row Level Security to write and get wrong.
- **Schema is no longer SQL.** `supabase/schema.sql` is kept only as a historical, commented-out reference; the real schema is the CloudKit `Entry` record type, which CloudKit auto-creates in the Development environment on first save (fields: `rawText`, `source`, `status`, `schemaVersion`, `category`, `subtag`, `title`, `entryDate`, `createdAt`, `userID`, `fields`, `workout`). `schemaVersion` moves to 6 to mark the migration.
- **Trade-off accepted.** CloudKit has no equivalent to a joined relational query or SQL aggregation; trend math (`TrendCalculator`, `StatusEngine`) now runs client-side over fetched records instead of at the database layer. Acceptable at this data scale (one user's own entries, on their own device), and it was already the direction the offline-first cache was pulling us.

## 15. ACTIVITY workout tracker + STYL muscle balance
- **A dedicated workout logger inside ACTIVITY.** A searchable exercise library (~190 movements) ships in the app, each exercise tagged with up to 2 primary and 2 accessory muscle groups. Logging a workout supports three speeds: pick an exercise and log sets/reps/weight, log just the movement with no numbers, or free-write the whole session and let the on-device model parse it into structured exercises.
- **On-device parsing, same pipeline as everything else.** A free-written workout runs through Apple Foundation Models with Guided Generation, matched against the exercise library, and returns a typed list of exercises rather than free text. No JSON parsing, no server round trip, consistent with `CLAUDE.md` rule 3.
- **STYL gets a muscle-balance read.** Using the muscle tags on logged exercises, STYL shows which body systems and muscle groups were trained recently and which have gone light, computed the same quiet way as everything else on STYL: no scores, no numbers invented, just what the log actually shows.
- **On-device "suggest a session."** When a muscle group has gone quiet, the on-device model can propose a session from the exercise library that fills the gap. This is a suggestion surfaced to the user, not an automatic entry; nothing is logged until the user acts on it.
- **Storage.** A logged workout's structured exercises live in the `workout` JSON blob on its `Entry` CloudKit record (ACTIVITY entries only), following the same "fixed fields where trend math matters, JSON blob for the rest" pattern already used for `fields`.
